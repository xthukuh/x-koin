What xKoin is

Internet that reaches where fibre does not, paid per cryptographically verified byte.

A Kenyan neighbourhood

One gateway sits on mains power with a mobile-data backhaul SIM. Solar-powered satellites extend the mesh with LoRa radio where there is no wiring at all. Clients attach with a phone or a small radio, over whichever medium is live.

Three mediums, one protocol

MediumModelGoodputRole
HomePlug AVEthernet-bridge PLC~10 MbpsBulk in-building data
KQ-130Fnarrowband PLC, UART 9600 baud~960 B/sTelemetry, receipts, control

Every frame is medium-agnostic: senders pick the live medium with the best recent delivery record, and three consecutive failures quarantine a medium for 2 seconds while the next-best one takes over. Grid failure degrades the mesh to LoRa; it does not stop it. Source: protocol/spec.md s1-s2.

From KES to XKN and back

A phone pays fiat, a bridge mints token 1:1, tickets settle earnings on-chain, and node admins cash back out to a mobile wallet.

Where the money went, one proof run

Tickets settled in this batch

The nine steps, kiosk to cash-out

  1. Phone pays via M-Pesa (Daraja STK) or Equitel (Jenga STK) at the kiosk.
  2. Bridge mints XKN 1:1 for the confirmed fiat (6 decimals: 1 base unit = 1 micro-KES).
  3. Kiosk issues an offline-verifiable Gas Voucher, signed by the kiosk root key.
  4. Client deposits XKN into escrow; only deposited balance can be drawn against.
  5. Client joins the mesh and browses; the serving node collects signed receipts.
  6. Receipts become EIP-712 tickets, settled on-chain by anyone who relays the batch.
  7. Node admins accrue earnings; the fee floor lands in the treasury automatically.
  8. Node admin claims earnings and cashes out via Jenga send-to-mobile.
  9. Anyone can trigger the treasury claim; funds can only ever reach the founder's cold address.

Why the token is not the risk

XKN is a prepaid unit pegged to KES by construction, never an investment.

The peg, by construction

What the contracts enforce
  • XKN is minted only against fiat already received, and burned only when fiat is paid out.
  • A per-bridge rolling-day mint cap bounds how much unbacked XKN a compromised bridge could ever create (50,000 KES default).
  • User balances cannot be burned by any key: bridgeBurn destroys only the bridge's own balance.
  • Escrow solvency is an assertion the proof checks, not a hope: escrow balance equals deposits plus earnings.
  • Settlement, deposits, withdrawals and treasury claims run with zero founder involvement, so the network keeps settling if the founder or the company disappears.

Risks we are managing, plainly

What can go wrong
  • Bridge float custody. The bridge holds customer float on Equity and M-Pesa merchant accounts; that float is a named trusted party, not a trustless one.
  • Regulatory approval pending. CBK e-money classification, CAK transit-resale licensing and CAK duty-cycle radio rules are open questions with counsel, not yet resolved.
  • Price undecided. The per-unit price is deferred until it can clear measured backhaul cost; a 500 uKES placeholder is used everywhere it must appear.

Security by construction

Eight invariants the peer layer enforces, each proved by a named test, plus a founder-safety layer that bounds what any single key can do.

The eight Laws

Founder-safety layer

"Zero-trust" describes the peer relay layer only: no peer must trust any other peer. The fiat boundary has named trusted parties, bounded like this:

  • Treasury claim() is callable by anyone and pays only the beneficiary; no key can redirect a single micro-KES.
  • Changing the beneficiary takes a 7-day public timelock, and the founder's cold key holds a veto.
  • Price is banded (1 to 50,000 uKES) with a 1-day cooldown: expensive to abuse, never a kill switch.
  • bridgeBurn is self-only: no key in the system can destroy a user's balance.
  • Bridge minting is capped per rolling day per bridge, so a compromised bridge leaks at most one day's cap.
  • Ownership transfer everywhere is two-step (Ownable2Step), so a mistyped address cannot brick ownership.

Key hierarchy

One key per job, coldest key for the job with the most money behind it. Source: docs/key-management.md.
